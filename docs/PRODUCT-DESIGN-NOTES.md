## 🎯 2026-05-27: 定位重构

### 这个产品到底是什么（2026-05-27）

```
高手的工作流本身是一套流程——
他们自己很多时候也说不清楚为什么要这么做，
只是从最终效果上看，确实很不错。

我要做的不是简单"抽取这套流程"，
而是建立维度，把高手隐性的判断能力显性化：
  - 可评估：每个维度可以独立打分
  - 可量化：不是"感觉不好"，是"action_clarity 0.38，低于阈值"
  - 可迭代：每轮有方向地改进，不是随机重试
  - 可视化：版本之间对比，看得到进度
  - 可收束：在现阶段能力范围内，收敛到最优

本质上在做的事：
  把"说不清楚但确实有效"的高手直觉
  → 拆成可度量、可追踪、可优化的工程体系

视频只是第一个应用场景。
这套方法论可以迁移到任何"生成了→好不好→哪里不好→怎么改"的生成式AI领域。
```

### 这个生意的本质（2026-05-27）

```
这是一个很难、护城河很深的事。

难在哪：
  - 评测维度建立极其费劲。不是写代码，是找到"客观变好"的标准
  - 收敛配方需要真实数据打磨，不能凭空编
  - 从"感觉不对"到"具体哪里不对"的映射，需要人工校准

护城河在哪：
  - 评测维度体系——越用越准，后来者没法跳过这个积累过程
  - 收敛配方——是经验和数据喂出来的，不是代码写出来的
  - 数据飞轮——更多用户 → 更准的评测 → 更好的结果 → 更多用户

增长模式：
  - 不是流量驱动的闪电扩张
  - 是数据飞轮驱动的缓慢积累
  - 更偏"理解"、"积累"、"用户口碑传播"
  - 前期慢，越往后越难被复制

与 ComfyUI 的关系：
  - ComfyUI 做的是执行——"你给我 Prompt，我给你图片"
  - ShotForge 做的是判断——"你给我的图片，哪里不对、怎么改"
  - 执行层容易被替代（模型在进步、工具在涌现）
  - 判断层才是终极护城河——"知道什么是好"永远比"能生成图"稀缺
  - 这条路人人都知道有价值，但没人敢碰——因为除了写代码，还需要：
    人工校准维度、积累案例数据、跟创作者反复沟通、读论文提炼方法
    每一步都消耗心力，且急不来
```

### 三件事

| 能力 | 做什么 | 当前状态 |
|------|--------|---------|
| **评测** (Evaluate) | 判断好不好、哪里不好 | 🚧 5个硬维度已设计，待实现 |
| **诊断** (Diagnose) | 为什么不好、根因在哪 | 📋 V2 规划 |
| **收束** (Converge) | 怎么改、改完验证、直到满意 | 📋 V3-V4 规划 |

### 关键架构决策（2026-05-27）

```
1. 评测分维度、诊断统一收束
   评测可以分专家（SubjectEvaluator, ActionEvaluator...）
   但诊断必须统一（IssueRegistry → Merge/Dedup → RootCause → Priority）
   原因：视频问题强耦合，各自修会互相破坏

2. 结构化 PromptTemplate
   之前：一整段 prompt → 评测说"不好" → 不知道怎么改
   之后：12 字段独立 → 评测定位"action_sequence 太抽象" → 定向改该字段
   这是使评测结果可回写的前提

3. RedesignPlan 包含三份清单
   本轮优先修 / 本轮保护 / 本轮暂不处理
   不只管"修什么"，也管"别动什么"——生产级思维

4. V1 只做硬目标，小模型可做
   主体存在性 (YOLO) / 数量 / 场景匹配 (CLIP) / 道具 / 动作发生 (VideoMAE)
   零 API 成本，快速验证闭环
```

### 下一阶段：范围收束

```
当前问题：目标太大，涉及 ComfyUI 平台对接 + 多模型切换 + 复杂剪辑
需要做：裁剪到开源第一版可交付的最小闭环

原则：
  - 窄而深，不是宽而浅
  - 减少平台对接，体现核心思路的完整性
  - 体现"中间路径"的核心价值——
    不是一次生成，而是迭代收敛到满意
    每次迭代都有记录，每次改动都可追溯

待裁剪决策（2026-05-28）：
  - 开源第一版要不要对接 ComfyUI？还是只用 Mock 体现思路？
  - 评测器做到哪一步？V1 五维全做还是先做 2-3 维？
  - 结构化 PromptTemplate 要不要在开源版放全量 12 字段？
```

## 🎯 产品核心理念（旧版留存）

### 这个产品到底是什么

```
不是: "另一个 AI 视频生成工具"（市场上有 100 个）
不是: "更好的 Prompt 工程工具箱"
不是: "自动做视频的机器人"

而是: "一个保留迭代历史的视频创作工作台"
    → 创作者不是在抽卡，是在打磨
    → 每次修改都被记录、每次改进都可以追溯
    → 从不满意到满意的路径，是可重复的方法论
```

### 三层价值模型

| 层次 | 价值 | 当前状态 | 难度 |
|------|------|---------|:---:|
| **Layer 1: 工作流价值** | 版本管理 + 迭代追踪 + 不必从头开始 | 功能有，交互差 | ⭐⭐⭐⭐⭐ |
| **Layer 2: 迭代价值** | 简单创意→收敛配方→越来越好的 demo | 未验证 | ⭐⭐⭐⭐ |
| **Layer 3: 场景价值** | 按行业/风格预设的评估+修正配方 | 未开始 | ⭐⭐⭐ |

### 开源前的价值定位

```
开源时对外说的故事:
  "ShotForge = 视频创作的 Git"
  → 保留每次迭代、追踪每次改动、版本对比一目了然
  
不要说的:
  → "自动生成更好视频"（未验证，说了会被打脸）
  → "AI 驱动的视频优化"（太泛，没差异化）
```

## 🧩 Layer 1: 工作流价值的打磨

### 问题 1: 版本如何呈现

```
现状: JSON diff + before/after 代码块 → 只有开发者能读
需要: 创作者视角的版本进化视图

待设计:
  □ 版本时间线：V1→V2→V3 的纵向流程
  □ 每个版本一个卡片：分数条 + 问题数 + 改了什么
  □ 卡片展开显示：before/after 的具体变化（非 JSON）
  □ 哪两个版本之间的跳跃最明显？要不要高亮？
  □ 版本之间要不要有 "回退到这个版本" 的操作？
```

### 问题 2: 迭代过程可感知

```
现状: 只有分数数字（3.2→4.1→5.7）
需要: 创作者"感觉"到在变好

待设计:
  □ 每个版本要不要有 "人话总结"？
     例: "V1→V2: 猫的动作从模糊变成清晰可辨"
  □ 修正 agent 干的活要不要展示给用户？
     "本轮的修正: 强化了 action_clarity，调整了 prompt 中的镜头描述"
  □ 要不要对比视频帧？V1 和 V2 的同一 shot 并排？
```

### 问题 3: 操作分层

```
现状: 10+ 控件全部平铺
需要: 创作者看到 3 个核心控件，高级选项折叠

待设计:
  □ 第一层（永远可见）: 创意输入 + 风格 + "生成"按钮
  □ 第二层（折叠）: Provider / 评估量表 / 迭代次数
  □ 第三层（设置页）: ComfyUI URL / API Key / 默认模型
  □ "运行"按钮的文案要不要随着模式变化？
     "开始打磨" vs "生成方案包" vs "一键评估"
```

### 问题 4: 工作流可视化

```
现状: 没有任何过程反馈
需要: 用户知道系统在干什么

待设计:
  □ 进度条/步骤条: Design → Generate → Evaluate → Redesign → Converge
  □ 哪一步在等待外部服务（ComfyUI API 要等几分钟）？
  □ 长时间任务要不要异步 + 轮询？还是保持同步等待？
  □ 如果 Redesign 循环 5 轮，用户要不要看到每轮的进度？
```

### 问题 5: 结果页信息架构

```
现状: 全部信息堆在右侧，线性滚动
需要: 有层次、有聚焦

待设计:
  □ 结果页的默认焦点是什么？
     "本轮评分 + 发现问题" → 最重要的，第一眼看到
  □ 辅助信息的层级:
     ▸ 评估详情 — 点击展开
     ▸ 修正计划 — 次要卡片
     ▸ 版本差异 — 折叠在时间线里
     ▸ 导出 — 底部固定栏
  □ 如果多轮迭代完成，默认展示哪一轮？
     最新一轮？还是完整时间线？
```

## 🧪 Layer 2: 迭代价值的验证

### 问题 6: 收敛配方从哪来

```
现状: 7 种修正策略是纯规则（correction_strategies.json）
      Mock quality_signals 是你编的
      
待回答:
  □ 真实的修正方向由谁决定？
     → 完全靠人工经验预设公式？
     → 还是用 VLM（GPT-4V/豆包视觉）做自动评估？
     → 还是最终让用户手工标注好/坏，系统学习？
  □ 如果 VLM 评估，成本和准确性怎么平衡？
     → 迭代阶段用便宜小 VLM，最终评测用强 VLM？
```

### 问题 7: 迭代真的在收敛吗

```
假设: "自动修正 PO 会让视频越来越好"
状态: 在 Mock 上能收敛（因为 Mock 的 quality_signals 是编好的故事）
      在真实模型上能否收敛？完全未知

待验证:
  □ 小模型（LTX Video）跑 3-5 轮，VLM 打分，分数在涨吗？
  □ 如果没涨 —— 问题在评估器不准还是修正策略不对？
  □ 修正后会不会在某些维度改善、某些维度退化？
```

### 问题 8: 人工参与在迭代中的位置

```
纯自动闭环: Evaluate → Suggest → Correct → Generate → Repeat
人工参与: Evaluate → 用户确认修正方向 → Correct → Generate → Repeat

待决策:
  □ 要不要在每次修正前问用户"这个方向对吗"？
  □ 要不要让用户可以在某轮迭代手动干预（改一个 Prompt）？
  □ 如果用户不干预，系统自己跑错了，用户怎么感知到？
```

## 🎨 Layer 3: 场景/风格配方的路线图

### 问题 9: 场景配方的粒度

```
概念: "游戏广告"场景 = 特定的评估权重 + Prompt 模板 + 修正策略

待定义:
  □ 一个场景配方包含哪些可配置项？
     必选: 评估维度权重、修正策略偏好、Prompt 模板前缀
     可选: 负面排除词、默认画幅、默认时长
  □ 预制几个场景？
     P0: 游戏广告、影视叙事（最容易有差异化）
     P1: 电商展示、风景、动画
     P2: 按社区需求
```

### 问题 10: 场景配方的效果如何衡量

```
你卖的就是"游戏广告配方"，客户买了以后:
  □ 怎么证明这个配方比通用 9 维好？
  □ 需要 A/B 对比数据吗？
  □ 配方效果好是因为权重调对了还是 Prompt 模板好？
     → 如果把权重和 Prompt 模板拆开，各自贡献多大？
```

## 📋 优先级判断（开门之前 vs 开门之后）

### 开源前必须搞定的（V4 之前）

| 项目 | 原因 |
|------|------|
| □ 运行 `shotforge full-loop` 不报错 | 开源基本要求 |
| □ 有至少一个真实的 Demo 视频 | 没视频没人信 |
| □ README 英文流畅 | 国际社区 |
| □ 版本管理和迭代闭环完整 | 这是核心差异化 |
| □ 基础 Web 页面能跑 | 让人快速尝鲜 |

### 开源前可以缓的

| 项目 | 原因 |
|------|------|
| □ UI 美化 (V5) | 丑不影响能用 |
| □ 场景配方 (Layer 3) | 冷启动时可以人工调 |
| □ VLM 自动评估 | 先用 Mock/人工评分 |
| □ 工作流可视化 | 可以先只有文字输出 |
| □ 操作分层 | 全显示也能用 |

### 开源后重点推的

| 项目 | 原因 |
|------|------|
| □ V5 产品化 UI | 留住用户的核心 |
| □ 迭代价值验证 | 给开源社区信心 |
| □ 第一个人工校准的场景配方 | 证明 Layer 3 可行 |
| □ 端到端 Demo 视频 | 社交媒体传播 |
